# Changelog

All notable changes to the Joomla skill are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html) where the SKILL.md content is treated as the public surface:

- **Major** — sections removed or restructured in a way that changes how the skill is used
- **Minor** — new guidance, new reference files, expanded coverage
- **Patch** — fixes, typos, clarifications, broken-link repairs

## [Unreleased]

### Fixed
- `README.md` — documents the v1.x upgrade path. Because the repository was renamed at 2.0.0, an existing install's marketplace is registered under the old name and `/plugin update` does **not** reach 2.0.0: the marketplace clone refreshes to the new commit, but the installed copy stays pinned in `~/.claude/plugins/cache/<marketplace>/<plugin>/1.1.0/` and keeps exposing only the single `joomla` skill. Removing and re-adding the marketplace fixes it. Found by hitting it on a real upgrade, not predicted.

## [2.0.0] — 2026-09-04

The repository stops being a single-skill repo. `skills/` is now a suite: the existing `joomla` reference skill plus **sixteen procedural workflows** — twelve non-overlapping security audits and four maintenance passes — with the build tooling generalised to discover skills rather than carry a hardcoded path.

The twelve audits are adopted as a complete set rather than a subset, and that is the cheaper option, not the more expensive one: upstream's audits cross-reference each other by name and the set is closed (every audit named inside another exists; none points outside the twelve). Taking a subset means rewriting each boundary statement to avoid naming a skill that isn't there — which the first five drafts of this work had to do, and which is now reverted in favour of the real references.

### Added
- `skills/audit-authz/SKILL.md` — audits component controllers for **missing** anti-CSRF token checks, missing authentication, and missing authorisation, across the administrator / site / api applications. Severity rubric led by unauthenticated upload (CRITICAL) and under-privileged create/edit/publish (HIGH). Reports, stops for user feedback, then writes per-fix plans to a `.gitignore`'d `.plans` directory for parallel execution.
- `skills/audit-controller-exposure/SKILL.md` — the complement: checks that *exist* but target the wrong permission or the component root asset instead of the record's own, backend-only tasks reachable from site/api controllers, and upload handling (allow-list vs deny-list, predictable stored names, web-executable storage, path traversal). Explicitly defers missing-check findings to `audit-authz` and SQL findings to `audit-sql-filtering`.
- `skills/audit-sql-filtering/SKILL.md` — filter / `getUserStateFromRequest()` / user-input values reaching queries without prepared parameters, severity scaled by application surface. Calls out the cases binding cannot cover — `ORDER BY`, `GROUP BY`, column lists, `list.fullordering` — where an allow-list is the only correct mitigation, and `quote()`/`escape()` used as a substitute for `bind()`.
- `skills/audit-xss/SKILL.md` — reflected, stored, and DOM-based XSS across layouts, views, modules, plugins, HTML mail, and script options. Records the Joomla-specific traps: `$this->escape()` is `ENT_COMPAT` so single-quoted attributes are unprotected, `HTMLHelper::_()` output is inconsistently pre-escaped, and `InputFilter` behaviour depends on per-group Text Filters with Super Users commonly set to "No Filtering".
- `skills/audit-jexec/SKILL.md` — PHP files missing `defined('_JEXEC') || die;`, including guards placed before a `namespace` declaration (a fatal), with the legitimate exceptions enumerated (`vendor/`, tests, build tooling).
- `skills/audit-object-access/SKILL.md` — IDOR/BOLA and per-record data isolation: the third question the two controller audits don't ask. Covers the classic Joomla split where `getItem()` applies `getAuthorisedViewLevels()` and `getListQuery()` doesn't, so the list view leaks titles the detail view would refuse; bulk `cid[]` operations authorising only the first ID; mass-assignment of `created_by` / `access` / `state` through `Table::bind()`; and 404-vs-403 differences as an oracle.
- `skills/audit-file-operations/SKILL.md` — traversal, Zip Slip, symlink escape (including between the check and the write), stream-wrapper schemes, and arbitrary read/write/delete. States plainly that Joomla's `PATH` input filter validates path *syntax* and does not prove containment beneath a permitted root — a common and load-bearing misreading — and that `Path::check()` only enforces the root it is handed.
- `skills/audit-sensitive-output/SKILL.md` — the non-HTML sinks: CRLF in headers, `Content-Disposition` filenames, CSV/spreadsheet formula injection, log forging, error disclosure (including what the API application's JSON exception rendering actually contains with Debug off), mail header and recipient injection, and cache isolation where a privileged response is served to another user.
- `skills/audit-code-execution/SKILL.md` — shell and command injection, `eval` / generated PHP / dynamic include, unsafe deserialisation including PHAR metadata, and attacker-selected callables, class names, and container lookups. Requires attacker control **and** a plausible gadget path before claiming deserialisation RCE, and labels unverified gadget availability rather than implying a working exploit.
- `skills/audit-ssrf-redirects/SKILL.md` — SSRF into loopback, private, link-local, and cloud-metadata destinations, with the requirement that every followed redirect is re-resolved and re-validated (validating only the submitted URL while the client follows a 302 is the standard bypass). Names Joomla's base64 `return` parameter as the CMS's most common open-redirect surface.
- `skills/audit-secrets-crypto/SKILL.md` — committed credentials and key material, tokens generated from `rand()` / `uniqid()` / time, comparisons that leak timing or tolerate type juggling, plaintext or reversible password storage, and lifecycle claims the design doesn't keep. Recommends rotation without performing it, and never prints a discovered secret in full.
- `skills/audit-package-surface/SKILL.md` — what the build ships versus what is in git: stray backups, dumps, CI config and source maps; executable PHP in `media/`; manifest `<files>` sweeping in more than intended; update-server transport and hash integrity; the `<scriptfile>` running with full privileges on install and update; and lockfile-aware dependency advisories treated as leads rather than proof. Does not contact registries or install dependencies without permission.
- `skills/joomla-deprecations/SKILL.md` — deprecated and removed core APIs sourced from the official [`joomla/Manual`](https://github.com/joomla/Manual) per-version-gap `new-deprecations.md` files, with a hard preference for one implementation across the whole supported range, capability checks (`method_exists`) over version checks, and a **mandatory** comment above each compatibility branch naming the version that forced it — without which those branches accumulate forever because nobody can tell what they were for.
- `skills/php-conservative/SKILL.md` — PHPCompatibility sweep over the range `composer.json` actually declares. Carries three things that are easy to get wrong: Rector is the wrong tool because it rewrites *to* a target and breaks the bottom of a range rather than reporting on it; PHPCompatibility 9.3.5 (2019) knows nothing past PHP 7.4, and since `testVersion` is not validated, asking about a version it has no data for reports **nothing**, indistinguishable from a pass; and Joomla's bundled Symfony polyfills make flagged 8.0/8.1 symbols false positives in extensions but **real** in standalone or CLI projects, so the suppression must not be applied there.
- `skills/e2e-tests/SKILL.md` — host-side PHPUnit driving a disposable Docker stack over real HTTP: the `tests/integration/` architecture, a `run.sh` that scrubs on entry as well as teardown so a crashed run cannot leak into the next, a version matrix derived from what the project declares rather than guessed, and a bootstrap that probes the site and says "run `docker/run.sh` first" instead of emitting connection-refused noise. Keeps the assertions that make a refusal test meaningful — assert the refusal **and** the absence of its effect, and confirm a new "must be refused" test can actually fail before trusting it.
- `skills/php-upcoming/SKILL.md` — the next, unreleased PHP, where static analysis is structurally useless: the sniffs have no data for a version that has not shipped, and since `testVersion` is unvalidated, asking about it reports nothing. Running the suite on that PHP with `E_ALL` is the only real check. Carries the two traps that make such a run look clean when it is not — a `php.ini` deliberately silencing `E_DEPRECATED` so notices do not break tests asserting on response bodies, and a pre-release image broken in ways unrelated to the project emitting startup warnings into the log you are reading — plus the requirement to filter tens of thousands of framework diagnostics down to first-party paths.
- `THIRD-PARTY.md` — MIT notice and copyright for the upstream work these derive from, a table mapping each adopted skill to its upstream workflow, what was not adopted and why, and a summary of what changed in adaptation. The repo stays GPL-2.0-or-later as a whole.
- `CLAUDE.md` — a maintainer's map, auto-loaded when working in this repo. Records the two skill shapes, the five invariants `scripts/validate.sh` enforces, the release ordering, and what deliberately does not belong here. Its centre is the **scope-boundary table**: which skill owns which question, and an explicit warning against the tempting refactor of merging twelve audits into one security skill, which would destroy the property that makes them useful — a generic input-validation audit reports shallowly on everything and thoroughly on nothing.
- `.codex-plugin/plugin.json` and `qwen-extension.json` + `QWEN.md` — native plugin manifests for Codex and Qwen Code, so both get **all seventeen skills** rather than only the extension-development guidance the universal package carries. Both hosts read the same `skills/<name>/SKILL.md` layout this repo already used, so the manifests are the only new files; no restructuring, no vendored install scripts.

All sixteen are adapted from [`nikosdion/pm-skill-demo`](https://github.com/nikosdion/pm-skill-demo) (MIT, Copyright © 2026 Nicholas K. Dionysopoulos). Upstream ships fifteen of them as an eight-line stub pointing at a shared `commands/*.md` **outside** the skill directory — a layout that cannot survive being zipped as a standalone skill, so every workflow here is inlined into its own self-contained `SKILL.md`. The prose was rewritten for a general Joomla 5+/6/7 audience rather than one vendor's conventions, and the Joomla-specific detail above was added throughout. Each file carries an attribution footer so the notice travels with a skill distributed on its own.

Two were additionally **retargeted or reconciled**, because adopting them verbatim would have contradicted guidance this repo already ships. `joomla-deprecations` moves from upstream's Joomla 4.4+ baseline to this suite's Joomla 5+ support window. `e2e-tests` is the larger case: upstream instructs converting in-process integration suites to Docker-over-HTTP ("in-process harnesses can't observe anything a real request couldn't"), while `references/testing.md` teaches exactly such a suite — real CMS classes loaded from a checkout, `tests/Integration/`, `phpunit --testsuite Integration`. Installed as written, the two skills would have told a user to rip out what the other had just taught them. The three layers are now presented as complementary, each answering a question the others cannot, and upstream's mandate that PHPUnit never be a project dependency and its exclusion of IIS are restated as project choices and a coverage gap rather than requirements. `php-upcoming`'s central step, hard-coded upstream to that harness's `run.sh --deprecations` and `.env` variable, is described by capability so it also applies to a project with an ordinary test suite.

Not adopted from upstream's nineteen: `plan-and-execute` (generic task orchestration, not Joomla, and command-shaped — `$ARGUMENTS` plus `model:` frontmatter — rather than skill-shaped; Claude Code covers this natively), `en-gb-consistency` and `machine-translation` (house-style and vendor-specific translation policy, which belong in a private plugin rather than a public generic repo).

One correction to an assumption made while planning this work: `e2e-tests` was initially deferred as "a Docker harness, not just a prompt". Upstream ships **no** harness code — no Dockerfiles, no `docker-compose.yml`, no `run.sh`, no PHP files anywhere in the repository. It is a 160-line `SKILL.md` describing an architecture for the model to build, and it is the only upstream skill whose content lives in `SKILL.md` rather than a `commands/` file. The real cost of adopting it was never vendored code; it was the contradiction with `testing.md` described above.

### Changed
- `scripts/validate.sh` — validates every `skills/*/` independently instead of the hardcoded `skills/joomla`. Two new checks, both catching failures the old script could not: frontmatter `name:` must equal the directory name (the release asset is named from the directory while Claude activates on the frontmatter name, so a mismatch silently misnames one of them), and names must be unique across the suite (duplicates shadow each other once installed). A third rejects any `../` link in a `SKILL.md` — the exact defect that makes upstream's stub layout unshippable as a zip. A fourth validates `.codex-plugin/plugin.json` (required fields, the fully-populated `interface` block a missing field of which makes the plugin unlistable rather than erroring, the `defaultPrompt` limits of 3 entries at 128 characters, and the `./skills/` pointer) and `qwen-extension.json` (including that the `contextFileName` it names actually exists). A fifth holds **all four manifests to the same version** — each host reads its own, so a stale one silently keeps serving the previous release to that host alone. A sixth compares `marketplace.json`'s `source.ref` against the plugin version: the ref decides which tree `/plugin install` actually fetches, nothing else validated it, and bumping both `version` fields while leaving the ref behind serves the previous release to every new installer — the same class of miss as the v1.1.0 version mismatch, one field over. Also asserts the universal skill exists, and the README grep no longer matches the repo name so a rename cannot trip it.
- `.github/workflows/release.yml` — builds **one zip per skill** in a loop, each rooted at its own folder (verified with `unzip -Z1`), because Claude.ai and Claude Desktop take one skill per upload. `joomla-skill-vX.Y.Z.zip` keeps its exact historical name so existing links resolve; the others are `<skill>-skill-vX.Y.Z.zip`. Release notes are composed into `release-body.md` with the asset table generated from each skill's own frontmatter description, so a new skill appears without editing the workflow. Validation now runs `scripts/validate.sh` rather than an inlined two-line check that had drifted from it. The resolved tag is constrained to `vMAJOR.MINOR.PATCH` before it reaches filenames, and `inputs.tag` is passed through `env:` rather than interpolated into the shell.
- `scripts/build-universal.sh` — hardcoded paths replaced by a `UNIVERSAL_SKILL` variable, with a header comment recording why the universal package deliberately ships **one** skill: the build flattens a skill into always-loaded rule files, and a procedural audit that reports then waits for the user either fires when nobody asked or is ignored entirely in that format.
- `skills/joomla/references/testing.md` — new `## Test Layers` table opening the reference, naming unit / in-process integration / E2E and what each answers, with the first two explicitly kept rather than converted. The `Don't test` bullet that read "Template HTML output (use E2E tests for that)" — pointing at something the repo did not have — now enumerates what genuinely needs a real request (template HTML, response headers and status, redirects, session behaviour, whether a refusal actually prevented the state change) and names the `e2e-tests` skill.
- `CONTRIBUTING.md` — rewritten for a suite: the reference-vs-workflow shapes and how each is edited, the closed audit cross-reference set, an "Adding a new skill" section matching the README's, the no-`../`-links rule and why, third-party notice obligations, and testing guidance for skill *routing* now that seventeen descriptions compete. The release section documents the per-skill zips and the two validation checks that guard the version and `source.ref` bumps.
- `README.md` — retitled for the suite, with tables of all seventeen skills and the reference-vs-workflow distinction. Codex and Qwen Code move out of the universal-package row into their own channel, since they now get the full suite; the universal package row drops Codex accordingly, as does the package's own generated README. The two new channels are labelled untested, because neither CLI was available to verify an end-to-end install. Installation gains a channel matrix (audits reach Claude Code, Claude.ai/Desktop, and manual install, but not the universal package) and per-skill download instructions. The Claude.ai steps are corrected to the current UI — **Customize → Skills → + → Create skill**, with code execution enabled first under Settings → Capabilities, since that toggle is what makes the Skills menu appear at all. New usage section for the audits and a contributor section on adding a skill.
- `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` — descriptions say "suite" and name the five audits, so `/plugin install` advertises what it actually delivers; `security` and `audit` added to the marketplace tags. The plugin `name` stays `joomla`, so `joomla@joomla-bible-study` is unchanged for everyone already installed.
- Repository renamed `claude-skill-joomla` → **`joomla-skills`**, since the old name describes a single skill the repo no longer is. In-repo references updated in `README.md`, `CONTRIBUTING.md`, both `.claude-plugin/*.json`, `scripts/build-universal.sh`'s generated README, and `skills/joomla/SKILL.md`'s issue-reporting line. Historical PR and issue links in earlier CHANGELOG entries are left alone — GitHub redirects the old path, and rewriting them would falsify where those links pointed at the time. `plugin.json`'s `name` is untouched, so `/plugin install joomla@joomla-bible-study` is unaffected either way.

  **Release ordering matters here, in this sequence:** (1) rename the repo on GitHub — redirects only work old-name → new-name, so until then the install commands in these files point at a repo that does not exist; (2) merge; (3) bump `version` in both `.claude-plugin/*.json` and convert this `## [Unreleased]` heading to the release version and date; (4) bump `marketplace.json`'s `source.ref` to the new tag — it is still `v1.1.0`, and leaving it there means `/plugin marketplace add` resolves under the new name but installs the old single-skill tree; (5) tag and push. Step 4 is now enforced by validation (below), but the rename in step 1 is not something a script can check.

## [1.1.0] — 2026-09-02

Minor release adding two new reference files: Joomla console (CLI) command authoring — the one extension surface the 1.0 line had explicitly marked out of scope — and the Web Services REST API (JSON:API), which previously had only a scaffold duplicated across three files and nothing on query conventions, errors, or consuming the API. Folds in the authentication / authorisation model from PR [#42](https://github.com/Joomla-Bible-Study/claude-skill-joomla/pull/42) (prepared 2026-07-25 against `component-advanced.md`, never tagged) — the two login gates, per-operation permissions, read-side ACL, failed-auth logging — now living in the new reference. Plus four new gotchas: two from #42 (401 with a valid token, `Log::add()` to an unregistered category) and two new — a system / task plugin loading under `php cli/joomla.php` and calling a web-only application method, and API language strings loading from `api/` rather than `administrator/`. All patterns verified against `joomla-cms` `6.1-dev` @ `5a28ad8` (`ConsoleApplication`, the `Application` / `Console` service providers, `SessionGcCommand`, `FinderIndexCommand`, `cli/joomla.php`; `ApiApplication`, `ApiRouter`, `ApiController`, `JsonApiView`, `ApiMVCFactory`, `JsonapiRenderer`, `ComponentDispatcher`, both `token` plugins, and the `com_content` API tier) and the Joomla Framework `console` / `application` packages. No existing reference files renamed.

### Added
- `references/console-commands.md` — new reference (~430 lines). Covers: the single `cli/joomla.php` entry point and `ConsoleApplication`; the **console plugin group** as the supported registration hook (`ConsoleApplication::execute()` imports `behaviour` / `system` / `console`); plugin scaffold (manifest with `group="console"`, J6.1 service provider, `SubscriberInterface` plugin subscribing to `ApplicationEvents::BEFORE_EXECUTE` — noting the constant resolves to `application.before_execute`, not an `on*` name); eager `addCommand()` vs **lazy registration through the container's `WritableLoaderInterface`** (the mechanism core uses for its own commands); a full `AbstractCommand` template (`$defaultName`, `configure()` with `addArgument` / `addOption`, `doExecute()` with `SymfonyStyle`, `Command::SUCCESS` / `FAILURE` / `INVALID` exit codes, `%command.name%` help placeholders, constructor injection); reaching component models via `bootComponent()->getMVCFactory()->createModel(..., ['ignore_request' => true])`; language loading; cron vs `scheduler:run` / task-plugin guidance; `--live-site` / `$live_site` for absolute URLs; enabling the plugin from `postflight()`; a table of every web assumption that breaks under the console (no `getDocument()`, `null` identity, `isClient('cli')`, `getInput()` is `Input\Cli` not the Symfony input, CLI-only session, queued messages flushed via `SymfonyStyle`, system plugins running on every invocation); a PHPUnit pattern using `ArrayInput` + `BufferedOutput` (works without an application because `mergeApplicationDefinition()` short-circuits); and commit-pinned upstream permalinks. Also records that `CliApplication` (standalone `cli/*.php` scripts) is removed in Joomla 6.
- `references/webservices-api.md` — new reference (~460 lines). Covers: the request flow through `ApiApplication` (`webservices` import → `onBeforeApiRoute` → `ApiRouter::parseApiRoute()` → `Accept` negotiation → per-route `public` check → `login()` with the **`api-authentication`** plugin group, so session cookies never authenticate `/api`); the `api/` tier layout and the fact that `ApiMVCFactory` falls back from the `Api` to the **`Administrator`** namespace for models and tables (no `api/src/Model/`); the webservices plugin with `BeforeApiRouteEvent`, the five routes `createCRUDRoutes()` registers and its `$publicGets` argument, read-only and custom `Route` registration; the `ApiController` contract (`$contentType` → model name via inflector, `$modelState`, `page[offset]` / `page[limit]` handled by core, `list[ordering]` validated against `filter_fields`, `filter[...]` translation being **opt-in** in the subclass, `allowAdd/Edit/Delete()` requiring `core.manage` plus the specific permission, `save()`'s PATCH merge and admin-form validation, `preprocessSaveData()`, 204 / 409 on delete); `JsonapiView` whitelists, `$relationship`, `prepareItem()`, pagination links, the `onApiGetFields` / `onGetApiAttributes` / `onGetApiRelation` extension events; the `<api>` manifest block and language loading from `api/`; **authentication and tokens** (`X-Joomla-Token` / `Authorization: Bearer`, the `base64("algo:userId:hmac")` token format HMAC-bound to `$secret`, `joomlatoken.*` profile keys, allowed-groups check defaulting to Super Users, `plg_api-authentication_token` + `plg_user_token` on by default and `basic` off, writing a custom provider); client query conventions; the exception → HTTP status table from `JsonapiRenderer`; the four CORS settings and preflight behaviour; consuming the API from curl, PHP `HttpFactory`, and browser JS (with the explicit note that admin JS should hit a `JsonView`, not `/api`); a gotchas list led by **401-vs-404 as the wiring diagnostic**; and a three-layer testing approach (filter-contract unit test, whitelist test, package-install acceptance test).
- `references/webservices-api.md` § Authentication and Tokens (from PR #42, relocated from `component-advanced.md`) — **API access is gated TWICE**: *Allowed User Groups* on the `User - Joomla API Token` plugin (empty = allow all groups) **and** the `core.login.api` ACL grant in Global Configuration; both default to Super Users, both must pass, and nothing in the UI says which one refused. The three steps of a least-privilege integration; the consequence that on a stock install the per-verb `core.create` / `core.edit` / `core.delete` checks are never exercised; the **permission-per-operation table**; **read-side ACL is your job** (`ApiController` enforces nothing on reads — the list model's `whereIn('a.access', $user->getAuthorisedViewLevels())` is the only barrier, and the render whitelists are the only column control); the seed stored raw in `#__user_profiles`; MAMP / Apache-CGI stripping `Authorization`; and **failed API auth is not logged by core** (`login(['username' => ''])` means `plg_actionlog_joomla::onUserLoginFailure` finds no user and returns).
- `references/gotchas.md` § API Returns 401 With a Valid Token — Two Gates, Both Super-Users-Only (from PR #42) — short-form entry pointing at the detail in `webservices-api.md`, placed where someone stuck on a 401 would look.
- `references/gotchas.md` § Log::add() to an Unregistered Category Is Silently Discarded (from PR #42) — `Log::addLogEntry()` dispatches only to loggers matching the entry's category, so an unregistered category builds the entry and drops it. Includes the two follow-on traps (registering twice writes every entry twice; registering at `Log::ALL` in production is unbounded growth) and the note that a bootstrap which only runs for the HTML document will not cover the API or console applications — register from the component's `boot()`.
- `references/gotchas.md` § Plugins Load Under the Console Application — new H2 entry slotted after `Task Plugin Language Keys` (plugin neighborhood).
- `references/gotchas.md` § Web Services API Loads Language Files From api/, Not administrator/ — new H2 entry directly after the console gotcha. `ComponentDispatcher::loadLanguage()` resolves against `JPATH_BASE`, which is `api/` under `ApiApplication`, so admin `.ini` strings — most visibly the admin form's validation messages surfaced in 400 responses — come back as raw keys unless the controller loads `com_example` from `JPATH_ADMINISTRATOR`. Documents that `system` / `task` plugin constructors and any bootstrap they `require` execute under the console, where `getDocument()` does not exist (`ConsoleApplication` implements `CMSApplicationInterface` but not `CMSWebApplicationInterface`), the resulting fatal that kills every scheduled task on the site, and the `instanceof CMSWebApplicationInterface` guard. Caught in production when `scheduler:run` died on a component whose task plugin required an asset-registering bootstrap file.

- Initial release of the Joomla 5+/6 skill packaged as a Claude Code plugin.
- `SKILL.md` covering coding standards, modern Joomla MVC architecture, PSR-4 namespaces, dependency injection, service providers, and the Web Asset Manager.
- `references/component.md` — full component scaffolding (frontend + backend).
- `references/module.md` — module structure with dispatchers.
- `references/plugin.md` — plugin event subscribers (`SubscriberInterface`).
- `references/library.md` — shared library packages.
- `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` so users can install via `/plugin marketplace add Joomla-Bible-Study/claude-skill-joomla`.
- GitHub Actions workflow that builds and attaches a `joomla-skill-vX.Y.Z.zip` to each release for upload into the Claude.ai consumer app.
